Two independent pieces have to exist in Keycloak before the operator is
useful:

1. **An admin credential for the operator itself** — so it can create
   groups and manage memberships via the Keycloak admin REST API.
2. **A Rancher OIDC client with a `groups` claim** — so that the groups
   the operator creates actually translate into Rancher access when a
   user logs in. Without this, the operator happily creates groups and
   bindings that grant nobody anything.

`scripts/keycloak-bootstrap.sh` performs both idempotently. The sections
below explain what it does and why, so you can also do it by hand in the
admin console.

---

## 1. Operator admin credential

The operator authenticates with the **password grant against
`admin-cli`** (`keycloak_client.py`). It does *not* support client
credentials / service accounts — the client ID is hardcoded to
`admin-cli` and there is no env var to override it. So you need a real
user with a password.

Create a dedicated user (do not reuse the realm super-admin):

| Field | Value |
|---|---|
| Realm | the realm holding the managed groups (→ `KEYCLOAK_USER_REALM = KEYCLOAK_REALM`), or `master` |
| Username | e.g. `rancher-operator` |
| Password | non-temporary — a temporary password makes the token request fail |
| **Email** | **required** — set one (e.g. `rancher-operator@noreply.invalid`) and mark it verified |
| Required actions | none |

> The email is not cosmetic. Keycloak's declarative user profile marks
> email required, so a user without one trips the `VERIFY_PROFILE`
> required action at authentication time and the password grant fails
> with `"error_description": "Account is not fully set up"` — even though
> the user's `requiredActions` list reads as empty in the admin API.
> This is the single most likely reason a freshly created operator user
> can't log in.

### Required roles

Assign these **client roles of the `realm-management` client** in the
target realm:

| Role | Needed for |
|---|---|
| `manage-users` | create/delete groups, add/remove users from groups (Keycloak files group writes under the users permission set) |
| `view-users` | read users, groups and group members (composite: includes `query-users`, `query-groups`) |

That is the minimal set for every call the operator makes:
`GET /users/{id}`, `GET /users?username=&exact=true`,
`GET /users?q=<attr>:<value>&exact=true` (attribute-mode members, see §4), `GET|POST /groups`,
`POST /groups/{id}/children`, `DELETE /groups/{id}`,
`GET /groups/{id}/members`, `PUT|DELETE /users/{id}/groups/{gid}`.
Members with `federatedIdentity` (see §5) add `GET /users/{id}/federated-identity`,
and with `createMissingUsers` on also `GET /users?idpAlias=&idpUserId=` and
`POST|DELETE /users`, all covered by the same two roles (verified with
an operator user holding only these two).
No `manage-realm`, no `admin` role.

> If the user lives in `master` instead of the target realm, assign the
> same two roles from the **`<realm>-realm`** client in `master`
> (e.g. `riigipilv-realm`) rather than from `realm-management`.

### Wiring it into the operator

```bash
--set config.keycloak.url=https://keycloak.example.com \
--set config.keycloak.realm=myrealm \
--set config.keycloak.userRealm=myrealm \
--set config.keycloak.username=rancher-operator \
--set config.keycloak.password='<password>'
```

`KEYCLOAK_URL` must be the **base** URL. The client builds
`/admin/realms/...` and `/realms/{userRealm}/protocol/openid-connect/token`
directly onto it — for Keycloak < 17 (legacy WildFly distribution) you
must include the `/auth` suffix in the URL.

### Verify

```bash
TOKEN=$(curl -s -d grant_type=password -d client_id=admin-cli \
  -d username=rancher-operator -d password='<password>' \
  https://keycloak.example.com/realms/myrealm/protocol/openid-connect/token \
  | jq -r .access_token)

# must return 200 with a group list, not 403
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TOKEN" \
  https://keycloak.example.com/admin/realms/myrealm/groups
```

## 2. Rancher OIDC client (the part that makes groups mean something)

The operator writes bindings whose principal is:

```
keycloakoidc_group://<groupName>
```

Both binding scopes use that same principal format, so nothing here is
scope-specific: project-scope `spec.keycloak.roleBindings` produce
ProjectRoleTemplateBindings, and (since 0.4.0) cluster-scope
`spec.cluster.keycloak.roleBindings` produce ClusterRoleTemplateBindings.
Cluster-scope groups are created under the *same* Keycloak parent group
as the project-scope ones.

Three things must line up for that principal to resolve at login time:

1. **Rancher must use the "Keycloak (OIDC)" auth provider** — not
   Keycloak SAML, not the generic OIDC provider. The provider name is
   baked into the principal prefix (`keycloakoidc_`); a generic OIDC
   config produces `oidc_group://` and the bindings will never match.
2. **The token must carry a `groups` claim.**
3. **The claim must contain the bare group name**, not the full path.
   The operator uses `groupName` alone, so a mapper with *Full group
   path* enabled emits `/parent/child` and nothing matches.

### Client configuration

| Setting | Value |
|---|---|
| Client ID | e.g. `rancher` |
| Client authentication | On (confidential) |
| Standard flow | Enabled |
| Direct access grants | Optional |
| Valid redirect URIs | `https://<rancher-host>/verify-auth` |
| Web origins | `https://<rancher-host>` |

### Group membership mapper

Add a **Group Membership** mapper on the client (Client → Client scopes →
`rancher-dedicated` → Add mapper → By configuration → Group Membership):

| Setting | Value |
|---|---|
| Name | `groups` |
| Token Claim Name | `groups` |
| **Full group path** | **Off** ← critical |
| Add to ID token | On |
| Add to access token | On |
| Add to userinfo | On |

> Keycloak ships a built-in `groups` client scope. It is not in the
> default scopes, and in several versions its mapper has *Full group
> path* set to **true**. Prefer a dedicated client mapper as above; if
> you use the built-in scope instead, open its mapper and turn full path
> off.

### Rancher side

In Rancher: **Users & Authentication → Auth Provider → Keycloak (OIDC)**

| Field | Value |
|---|---|
| Client ID | `rancher` |
| Client Secret | from Keycloak → Client → Credentials |
| Issuer | `https://keycloak.example.com/realms/myrealm` |
| Rancher URL | `https://<rancher-host>` |

Enable it **before** the operator reconciles its first CR — Rancher can
reject a `groupPrincipalId` for an auth provider that is not configured.

### Verify the claim end to end

```bash
# using the direct access grant on the rancher client (enable temporarily)
curl -s -d grant_type=password -d client_id=rancher -d client_secret='<secret>' \
  -d scope=openid -d username='<test-user>' -d password='<pw>' \
  https://keycloak.example.com/realms/myrealm/protocol/openid-connect/token \
  | jq -r .id_token | cut -d. -f2 | base64 -d 2>/dev/null | jq .groups
```

Expect bare names — `["p-abc-admin"]`, **not** `["/parent/p-abc-admin"]`.

## 3. Group naming constraints

- **Names must be unique realm-wide.** `get_group_by_name` searches
  top-level groups and one level of subgroups and returns the first
  exact name match (`keycloak_client.py:107-116`), and Rancher principals
  are name-only. Two same-named groups under different parents will
  collide. Namespace them, e.g. `<project-slug>-admin`.
- **Only one level of nesting is resolvable.** The CR's
  `keycloak.parentGroupName` → `roleBindings[].groupName` shape (parent →
  child) is exactly what the lookup supports. Deeper hierarchies created
  by hand won't be found.
- The operator tags what it creates with the group attribute
  `managed_by=rancher-keycloak-operator`. Handy for auditing; it is not
  used for filtering.

## 4. Looking members up by a user attribute

Each CR member names a Keycloak user in one of three ways:

| Member fields | `userIdentifier` is |
|---|---|
| `lookupByID: true` (default) | the Keycloak user UUID |
| `lookupByID: false` | the Keycloak username |
| `lookupAttribute: <name>` | the value of user attribute `<name>`; `lookupByID` is ignored |

The attribute form exists for deployments where Waldur and Rancher
authenticate against **different** Keycloaks, so neither the UUID nor
necessarily the username is shared. The identifier both sides do share
(typically a national civil code) is then sent by the site agent, and
the Rancher-side Keycloak may hold it as a user attribute instead of
the username:

```yaml
members:
  - userIdentifier: "38001010001"
    lookupAttribute: civil_code
```

If the Rancher Keycloak stores the civil code *as the username*, use
`lookupByID: false` instead — no attribute setup is needed.

What has to hold for attribute lookup to work:

- **Only administrators may write the attribute.** Attribute lookup
  gives the grant to whoever holds the value, so a user who could edit
  the attribute in the Account Console, at registration or on the
  first-broker-login profile review could copy someone else's civil
  code into their own profile and receive that person's access. On
  Keycloak 24+ (declarative user profile always on), declare the
  attribute in *Realm settings → User profile* with **edit permission
  `admin` only** (view `admin`), or fill it from an identity-provider
  or LDAP mapper. Leaving it undeclared works only with
  *Unmanaged attributes* set to *Only administrators can write*
  (`ADMIN_EDIT`). Never use *Enabled*, which lets users edit it.
  The operator enforces this: before matching by an attribute it reads
  `GET /users/profile`. If users can edit the attribute, or the profile
  can't be read, it logs an error, adds nobody by that attribute, and
  stops keeping current members on the strength of it. The check is
  cached for five minutes, so fixing the realm needs no restart.
- **The attribute must be visible to the admin API.** An attribute that
  is neither declared nor allowed as unmanaged is neither searchable
  with `q=` nor returned in group member listings, so every lookup
  silently finds nobody and the user is never added.
- **The operator credential needs `view-users`** (already part of the
  minimal role set in §1); the search is `GET /users?q=<name>:<value>`.
- **Values must match exactly** what the site agent sends: same
  attribute name, same value, no extra whitespace or prefix such as a
  country code. The operator re-checks every search hit against the
  returned attributes and keeps only exact matches, so a substring
  match in Keycloak's search can never resolve to the wrong user.
- **Values must be unique.** Keycloak does not enforce uniqueness of
  attributes. If a value matches more than one user, the operator adds
  nobody and logs an error with the attribute name and match count
  (values are masked in logs, e.g. `3800…01`).

Status `syncedMembers` echoes the attribute value for members matched
by attribute (as it echoes the username for username-mode members), so
the site agent can confirm each grant against what it submitted.

## 5. Pre-creating users who have not logged in yet

When Waldur and this Keycloak sign users in through the **same upstream
identity provider** (TARA, say), Keycloak creates a user only during the
person's first login. A member added in Waldur before that is not found
(`User … not found in Keycloak`), and when they do log in, their first
token has no `groups` claim, because the operator adds them on its next
reconcile. Rancher grants nothing until they log in again.

With `createMissingUsers` on, the operator creates such a user up front,
already linked to the identity provider, so the first login lands on it
with its groups in place. It applies to members that look like this:

```yaml
members:
  - userIdentifier: ee38001010001      # username, lowercase
    lookupByID: false
    federatedIdentity:
      provider: tara                   # identity provider alias in this realm
      userId: EE38001010001            # the id the provider sends (its `sub`), case preserved
    firstName: Mari                    # optional, for the user created up front
    lastName: Maasikas
```

A member with `federatedIdentity` names a person by their id at the
provider, so on every reconcile of a username-mode member (`lookupByID:
false`, no `lookupAttribute`):

1. **The user found by username must hold exactly that link.** Only then is
   it added to the group, and it stays in the group only while it holds the
   link. A local account or a leftover user that happens to have the
   username gets nothing, and a user linked to a different id is removed
   with an error. This applies even with `createMissingUsers` off, so check
   that existing users' links match before the field is sent. Members
   without `federatedIdentity` keep plain username matching. A confirmed
   link is re-read every five minutes, so a link an admin removes stops
   counting within that time. If Keycloak cannot be asked, the member is
   kept and the error is reported through `MembershipSynced`.
2. **If no user has the username**, and `createMissingUsers` is on, the
   operator first checks that no user holds the identity yet. If one does,
   under another username, nothing is created and an error is logged.
   Otherwise it creates the user **with the link in the same request**
   (`POST /users` with `federatedIdentities`), so no crash or timeout can
   leave the user without its link.
3. **The result is verified** before the user is added. Keycloak checks
   neither side of a link:
   - A link to an alias the realm does not have is silently dropped, while
     the request still succeeds (`201` here, `204` on the separate link
     endpoint).
   - Several users may hold the same provider identity. Every login with
     that identity then fails with an internal error
     (`More results found for identityProvider=…`).

   So the new user must hold the link and be its **only** holder. If not, or
   if verifying fails, the user is deleted again.
4. **An existing user is never linked.** Linking an account the operator
   did not create would hand it to whoever holds the external identity.
   When two CRs create the same member at once, one of the creates gets a
   `409`. That reconcile adopts the user only if it already holds exactly
   the link.

**Names.** A user created this way gets the member's `firstName` and
`lastName`, if the CR carries them, so admins see who it is before the
person first logs in. They are set only when the user is created: the
operator never changes the profile of an existing user. After the first
login the identity provider's mappers own the profile, and with sync mode
*force* they overwrite these names with the ones the provider sends.

A failure for one member, such as a refused create or a timeout, is logged
and reported through `MembershipSynced`. The binding's other members still
sync.

**Recovering a broken user.** A user created from a wrong `userId` (wrong
case or a missing prefix) can never be logged in to. The person's login
ends at Keycloak's *account already exists* page, because the username is
taken by a user that isn't linked to them. The operator removes such a user
from its groups and logs the mismatch. Fix the `userId` the CR is generated
from, then delete the user in Keycloak, and the next reconcile recreates it
correctly. The same applies to an unlinked user left behind by any other
means.

Requirements:

- **`userId` must be the id Keycloak stores for the provider**, which is
  case-sensitive. Open any user who has logged in through the provider →
  *Identity provider links* → *User ID* and compare.
- **`userIdentifier` must be lowercase** and equal to the username Keycloak
  would give that person (e.g. from a `${CLAIM.sub}` username template).
  Keycloak stores usernames lowercased; a mixed-case identifier is refused
  rather than created, since it would never match on later reconciles.
- **The identity provider must fill the user profile on login.** A
  pre-created user has only a username. Set the provider's mappers to sync
  mode `FORCE` for the attributes it sends (email, first and last name). If
  the realm's user profile requires an attribute the provider does not send,
  for example email from TARA, Keycloak shows an *Update profile* form on
  login. It does that for every first login from that provider, whether the
  user was pre-created or not, so making such attributes optional in
  *Realm settings → User profile* is a realm decision, not a requirement of
  this feature.

Users the operator created are not deleted when they leave every project or
never log in.

Enable it with the helm value `config.keycloak.createMissingUsers: "true"`
(env `KEYCLOAK_CREATE_MISSING_USERS=true`). It is off by default: it decides
that the realm holds users who have never logged in.

## 6. Keeping members a Keycloak admin added by hand

The operator makes each group's membership match the CR: whoever the CR does
not name is removed. A deployment that still grants Rancher access in Keycloak
while moving to Waldur can instead keep those people and have the CR's writer
import them.

Set `config.keycloak.externalMemberPattern` (env
`KEYCLOAK_EXTERNAL_MEMBER_PATTERN`) to a regular expression the whole
username must match, for example `^[a-z]{2}[0-9]+$` for usernames that are
national identity codes. Keycloak stores usernames in lowercase, so a pattern
with uppercase letters never matches. An invalid pattern stops the operator at
startup. With `existingSecret`, add the variable to that secret yourself.

### What the operator remembers

To tell "the writer dropped them" from "someone added them in Keycloak", the
operator keeps a history per group in `status.memberHistory`, by Keycloak user
id. It is written back even when a reconcile fails, and it is kept for groups
that leave the spec:

- **managed**: users the spec named;
- **removed**: users the operator took out, and when;
- **external**: users kept although the spec never named them, and since when.

### The rules

For a group member the spec does not name, in this order:

1. **The spec had them** (managed): the writer removed them. They are taken out
   and recorded as removed.
2. **They were removed less than the grace period ago**: someone or something
   put them back, for example another CR on a shared cluster group that still
   carries the old spec. They are taken out again.
3. **Their username does not match the pattern**: they are taken out, as
   without the pattern.
4. **Otherwise** they were added in Keycloak. They are kept and listed in the
   binding's `status.*RoleBindings[].externalMembers` (username, first and
   last name and identity-provider links, never their email), and left out of
   `syncedMembers`. If the writer names them within the grace period they
   become managed. If not (the import was refused, or the writer cannot see the
   grant, for example because the person has not accepted the offering's terms),
   they are taken out and not reported again until the grace period has passed.

The grace period is `config.keycloak.externalMemberGraceSeconds` (env
`KEYCLOAK_EXTERNAL_MEMBER_GRACE_SECONDS`), 900 seconds by default. A person
the writer removed and a Keycloak admin adds back *after* the grace period
counts as a new addition and is imported again.

The Waldur site agent's `rancher-kc-crd` plugin, with `import_external_members`
on, turns reported members into Waldur roles; on its next cycle they are
ordinary members of the CR.

### Before turning it on

- **Anyone who can edit these groups can grant access in Waldur.** That is the
  point of the feature, but it makes Keycloak group admins as powerful as the
  people who manage the team in Waldur. The pattern limits which accounts can
  be imported, not who adds them.
- **The CR status is trusted.** The writer imports whoever `externalMembers`
  lists, and `memberHistory` decides who is listed. Keep write access to
  `managedrancherprojects/status` in the operator's namespace to the
  operator's service account.
- **Rollout order.** Have the CR writer emit a binding for every mapped role
  first (the site agent does with `import_external_members` on), and let one
  cycle pass before setting the pattern. Members left behind in a group whose
  binding had disappeared from the CR are then removed instead of imported.
- **A refused import does not stick.** Someone the writer never takes over is
  removed after the grace period and stays out for another grace period;
  after that, being put back counts as a new addition again. A Keycloak admin,
  or an identity-provider mapper that assigns groups at login, can therefore
  keep such a person in the group about half the time. Treat the grace period
  accordingly.
- **The CR status carries personal data**: `externalMembers` lists usernames
  and identity-provider ids, which are civil codes in such deployments. Read
  access to the CRs exposes them, as it already does for the spec.
- **A CR created afresh starts with no history**, so everyone in its groups who
  matches the pattern and is not in its spec is reported as external once.
  People the writer already grants are matched to those grants.

Empty (the default) keeps today's behaviour: every member the CR does not
name is removed.

## 7. Cleanup semantics to be aware of

On CR deletion the operator removes members (by the UUIDs Keycloak
lists for each group, whatever form the spec used) and deletes the CR's
project groups. Cluster-scope groups and the per-cluster parent group are
shared by every CR on the same cluster (one per ResourceProject of a Waldur
Resource), so they stay while any other CR for that cluster exists. The
last CR removes the cluster groups as well.

The parent group is deleted **only if it has no child groups left**.
Keycloak deletes a group's subgroups along with it, so this check is what
keeps one CR's deletion from taking its siblings' groups. It reads
`subGroupCount` from `GET /groups/{id}`: Keycloak 26 leaves `subGroups`
empty there and lists children only under `/groups/{id}/children`.
Pre-existing groups adopted by name are deleted the same way as ones it
created — don't point a CR at a group you also use for something else.
