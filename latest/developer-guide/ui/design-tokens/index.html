    Design Tokens

    How colours are defined — the ramps, the semantic roles built on them, the Tailwind utilities that expose those roles — and how to change one.

    • The rule and file format: ramps as data
    • Semantic roles: the neutral text scale, surfaces, borders, the status matrix, brand
    • Tailwind utilities for the roles: text-tertiary is var(--text-tertiary)
    • Bootstrap colour utilities: retired, and why
    • The brand colour in SCSS
    • Guards: tests and lint rules that keep all of the above true

    The rule

    Colour ramps are edited in one file: packages/design-tokens/tokens/colors.json. Never edit the file generated from it:

    Generated file Consumer
    packages/design-tokens/src/css/primitives/colorRamps.css Tailwind and CSS variables (--color-gray-500, bg-success-600), declared once in @theme static 
    1
2
3
4
    yarn tokens:generate   # rewrite colorRamps.css from the JSON
yarn tokens:check      # exit 1 if it is stale (also run by the unit tests)
yarn tokens:audit      # dead/ghost tokens, redundant aliases, new duplicate roles (exit 1)
yarn tokens:duplicates # the same, plus the full duplicate value-profile report

    generateTokens.test.ts fails when a generated file no longer matches the JSON, whether the JSON or the output was edited. The fix is always yarn tokens:generate. tokenAudit.test.ts fails when an unexempted token has zero call sites in consumer code, when consumer code references undeclared ghost tokens, when duplicate semantic token declarations exist across stylesheets, or when two semantic tokens resolve to the same value in both themes and the pair is not in DUPLICATE_BASELINE (see Guards).

    File format

    1
2
3
4
5
6
    "success": {
  "description": "Optional; becomes a comment in the output.",
  "steps": {
    "50":  { "light": "#ecfdf3" }
  }
}

    Optional ramp-level key: css: false (leave the ramp out of the CSS).

    Colours are lower-case #rrggbb; the generator rejects anything else. A step has one value: the key is light for history, and the generator rejects a dark one. Ramps are physical and the same in both themes; dark UI picks other steps through the semantic tokens. (The Sass ramps used to be theme-inverted for a separate dark compile, style.dark.scss, which is gone.)

    Gray in dark mode: gray and gray-dark

    Dark UI wants neutral grays where the light gray is blue-tinted (500 is #667085 vs #85888e), so there are two CSS ramps, both physical (step 900 is dark in both):

    • --color-gray-N (gray) is the same in both themes: nothing overrides the variable per theme, and text-gray-500 is --color-gray-500 in dark mode too (Bootstrap no longer emits its theme-inverted .text-gray-N; see Bootstrap colour utilities). So a bare gray is dark-on-dark in dark mode: for neutral text, surfaces and borders use the semantic utilities, or pair the step with its gray-dark mirror (bg-gray-300 dark:bg-gray-dark-600).
    • --color-gray-dark-N (gray-dark) is the palette for dark surfaces. It is read by the dark-theme blocks of background.css and button.css, and by the dark sidebar style in sidebar.css (a fixed look that is dark in either theme, so it reads gray-dark unconditionally, while the light style reads gray). A component that needs a dark-specific gray writes dark:bg-[var(--color-gray-dark-800)] or dark:bg-gray-dark-800.

    Sass never reads gray-dark. Its values are what the old theme-inverted SCSS grays were in dark mode, re-indexed: gray-dark-N was the dark value of the mirrored $gray-N (25 ↔ 950, 50 ↔ 900, …). The mirrored-ramp-color() mixin keeps that pairing for one-off SCSS colours.

    Semantic roles

    The semantic layer (packages/design-tokens/src/css/semantic/) names what a colour is for. Each role is defined for both themes in one file; prefer a role to a ramp step whenever one fits. Values below are light / dark; gray-dark-N is written dN.

    Neutral content: --text-* (text.css)

    One ladder for text and icons, strongest first. Every step is a distinct gray in both themes.

    Token Light Dark Use
    --text-primary gray-900 d25 Headings, primary content
    --text-secondary gray-700 d200 Body copy, strong labels
    --text-tertiary gray-600 d300 Supporting text, menu items
    --text-quaternary gray-500 d400 Muted text, subtitles, placeholders
    --text-quinary gray-400 d500 Faint text, decorative icons
    --text-senary gray-300 d600 Disabled marks, inactive indicators
    --text-disabled gray-300 d500 Disabled input and date-picker text

    The names follow the Untitled UI ordinal convention, and they match the Tailwind utilities (text-secondary … text-senary). There is no separate --fg-* neutral family any more: --fg-primary … --fg-senary, --text-body, --text-subdued and --text-muted were merged into this scale. The renames, for reading old code or branches:

    Old New
    --fg-primary --text-primary
    --text-body, --fg-secondary --text-secondary
    --text-subdued, --fg-tertiary --text-tertiary
    --text-secondary, --fg-quaternary --text-quaternary
    --text-muted, --fg-quinary --text-quinary
    --fg-senary --text-senary

    Note the trap in the middle row: the old --text-secondary was gray-500 and is now --text-quaternary; the new --text-secondary is gray-700.

    text.css also holds --fg-white (white text or icon in both themes). Every brand role is in brand.css: the brand marks (--fg-brand-primary, --fg-brand-secondary, --fg-brand-accent), brand text (--text-brand-primary / --text-brand-secondary, and --text-primary-on-brand on a brand fill), brand surfaces and borders, and the focus ring.

    Surfaces: --bg-* (background.css)

    Token Light Dark Use
    --bg-primary white d950 The base surface
    --bg-primary-hover gray-50 d800 Hover/highlight of a row on that surface
    --bg-secondary gray-50 d900 Faint panel, alternate section
    --bg-tertiary gray-100 d800 Avatar tiles, chips, pressed states
    --bg-quaternary gray-200 d700 Stronger fill (selected day, track)

    Plus --page-bg and --card-bg, and the brand fills --bg-brand-*.

    Borders and lines: --border-* (borders.css)

    Token Light Dark Use
    --border-primary gray-300 d700 Input and control borders
    --border-secondary gray-200 d800 Card and section borders (the default)
    --border-tertiary gray-100 d800 Hairlines
    --border-divider gray-200 d700 A drawn line: rules, step connectors
    --border-divider-medium gray-300 d600 A line that must show on any surface: timeline and stepper connectors, dashed outlines (border-divider-medium)
    --border-divider-strong gray-400 d500 A strong line: drag handles
    --border-brand brand-300 brand-400 Subtle brand border
    --border-brand-solid brand-600 brand-500 Selected/active brand border

    State borders (success, warning, danger) are in the status matrix, not here.

    State colours: the status matrix (status.css)

    Every colour that signals a state — badges, banners, alerts, health indicators, validation errors, destructive menu items, status dots, focus rings on an invalid control — reads one matrix:

    Slot success / warning danger Use
    -bg 50 / 900 50 / 900 Tinted surface (pill, banner, row)
    -border 300 / 400 300 / 400 Subtle border, neutral or tinted surface
    -solid 600 / 500 600 / 500 Saturated fill or ring
    -fg 700 / 400 700 / 300 Text, icons and dots

    as --status-{success,warning,danger}-{bg,border,solid,fg}, plus -bg and -fg only for info (50 / 900 and 600 / 300) and neutral. Steps refer to the intent's ramp (danger reads error-*).

    Each slot has a Tailwind utility (tailwind/theme.css), named like Bootstrap 5.3's:

    Slot Utility
    -fg text-danger, text-success, text-warning, text-info, text-neutral
    -solid bg-danger, border-danger, …
    -bg bg-danger-subtle, …, bg-info-subtle, bg-neutral-subtle
    -border border-danger-subtle, …

    Use these, not the arbitrary form: no-raw-status-ramp autofixes text-[var(--status-danger-fg)] to text-danger. A slot outside that table (-solid as text, say) keeps the arbitrary form.

    • One -fg for every surface. Each -fg clears WCAG AA (4.5:1) on the card, on the page and on its own -bg, in both themes, so the same slot serves text on a neutral surface and text on a tinted pill. statusContrast.test.ts reads the CSS and enforces it; this is why danger's dark -fg is error-300 (error-400 on error-900 is 3.5:1).
    • danger, not error. Roles are named by intent, like the button, ActionItem and Badge variants; error is only the red ramp's name.
    • No raw ramps for states. bg-success-50 dark:bg-success-900 is bg-success-subtle; the no-raw-status-ramp lint rule reports the raw form. A deliberate step outside the matrix (Badge's outline tone, FeaturedIcon's tile tint, a halo ring) carries an eslint-disable with its reason.
    • Retired names: --text-{error,warning,success}-primary, --fg-{error,warning,success}-*, --border-{error,success}, --border-*-solid, --bg-{error,warning}-primary, --status-*-text and --status-*-dot all became -fg, -border, -solid or -bg slots.

    Badge's solid and light tones and Progress's fills read -solid / -bg / -fg directly, so a badge, a bar and an alert of the same intent cannot drift apart.

    Brand

    --brand-* is the tenant's runtime ramp (initBrandTokens()); --brand-color is its step 600. Tailwind sees the ramp through the --color-brand-* bridge in tailwind/theme.css (bg-brand-50, text-brand-700): physical steps like gray-N, the same in both themes. A brand-tinted surface is bg-brand-subtle (--bg-brand-subtle: brand-50, brand-900 in dark). Brand text and lines are text-brand / border-brand / outline-brand, which read the role --text-brand: --brand-color in light, --brand-300 in dark, where the tenant colour is too dark to read. A solid brand fill is bg-[var(--bg-brand-solid)]. Semantic brand roles: --bg-brand-*, --border-brand*, --fg-brand-*, --text-brand*, --focus-ring-color.

    Tailwind utilities for the roles

    tailwind/theme.css in this package holds every utility whose value is a variable defined elsewhere: the semantic roles and the runtime brand ramp. A primitive declares its own utility, since there the variable is the token (--color-gray-500, --radius-md); a bridge never lives next to a value, and a value never changes per theme outside semantic/. It bridges the roles to Tailwind with property-scoped theme keys (--text-color-*, --background-color-*, --border-color-*), not --color-*. A --color-* entry fans out to every colour utility — bg-, border-, ring-, fill-, … — and a text gray is not a background. Scoped keys give exactly one utility per role, and one rule:

    It ships in the package and index.css imports it, so waldur-homeport, Storybook and the micro-apps all get the same utilities; waldur-ui and shell depend on them. tailwindTheme.test.ts fails if they use a semantic utility the package does not declare.

    A utility and the variable of the same name are the same colour.

    Utility Is
    text-primary … text-senary var(--text-primary) … var(--text-senary)
    bg-primary, bg-primary-hover var(--bg-primary), var(--bg-primary-hover)
    bg-secondary, bg-tertiary, bg-quaternary var(--bg-secondary) …
    border-primary, border-secondary, border-tertiary var(--border-primary) …
    border-divider var(--border-divider)
    text-brand, border-brand, outline-brand var(--brand-color)
    • No exceptions. text-primary used to be the brand colour; its brand uses were renamed to text-brand, and text-primary is now var(--text-primary) like every other step.
    • Prefer the named utility to the arbitrary form: text-quaternary, not text-[var(--text-quaternary)]. Roles with no utility (--bg-brand-*, --text-brand-*) use the arbitrary form; the status matrix has its own (above).
    • There is no bg-secondary text colour, text-secondary background and so on: each name exists only for the property it belongs to.
    • Removed aliases: bg-surface-faint (now bg-secondary), bg-bg-primary (bg-primary), border-border-* (border-*), and the --color-surface-faint, --color-bg-primary, --color-border-*, --color-secondary, --color-tertiary, --color-quaternary keys. A brand border that used to be border-primary is now border-brand.
    • Bootstrap's neutral classes were migrated to the utility with the identical value in both themes: text-muted → text-quaternary, text-gray-400/500/600/700 → text-quinary/quaternary/tertiary/secondary, bg-body → bg-primary, bg-gray-100/200 → bg-tertiary/bg-quaternary, border-gray-200 → border-divider. The rest followed when Bootstrap's colour utilities were retired (next section).

    Bootstrap colour utilities

    Bootstrap's utility API emitted .text-*, .bg-* and .border-* colour classes with !important, in the bootstrap cascade layer. An !important declaration in an earlier layer beats every Tailwind utility, important or not: a class Tailwind also defined (text-gray-500, text-white) silently painted Bootstrap's compiled colour, theme-inverted in dark mode, and no dark:/hover: variant beside it applied.

    Bootstrap emits no colour utility any more. src/styles/bootstrap/_utilities.scss removes color, background-color, border-color and border-top/-end/-bottom/-start from $utilities, and the border: 0 .border-0 from its border utility. (Its width utilities stay: .border-0 … .border-5, .border-top-0, … set only border-width.) Every colour class is Tailwind's and follows the design tokens. ($theme-colors is an empty map, so no Bootstrap component emits a contextual colour either.)

    Bootstrap's old class names paint nothing now, except those Tailwind defines itself (the status utilities). They were migrated as:

    Bootstrap Now
    text-danger / -success / -warning Tailwind's text-danger, … (the -fg slot; a step darker in light mode)
    bg- / border- danger / success / warning Tailwind's bg-danger, … (the -solid slot)
    text-info, bg-info text-info-600 dark:text-info-300, bg-info-600
    text-dark, text-body text-primary
    text-gray, text-muted, text-reset text-tertiary, text-quaternary, text-inherit
    bg-light, bg-dark bg-tertiary dark:bg-quaternary, bg-[var(--bg-primary-solid)]
    border-top / -bottom / -start / -end border-t-[1px] border-t-secondary, … (l / r for start / end)
    text-gray-800/900, border-gray-300 text-primary, border-primary

    FormText (waldur-ui) is text-tertiary; give it className="text-quaternary" for a quieter line, or text-danger for an error.

    • The waldur-custom/no-bootstrap-color-utility lint rule reports a retired name with its replacement, and a class built as `text-${variant}` (map each variant to a full class name). It skips strings that hold a name rather than a class list: a BaseButton variant="text-danger", an object key outside classNames()/cn(), a comparison, a TypeScript literal type.
    • src/tailwindBootstrapColors.test.ts compiles the Metronic SCSS and checks it emits no !important colour class, and that Tailwind defines none of the retired names.
    • The same trap on borders: Bootstrap's .border is still emitted, and it is border: 1px solid var(--bs-border-color) !important, so a Tailwind border colour next to it never paints. Use border-[1px] (border-t-[1px], …) for the width and give every state an explicit colour, e.g. rounded border-[1px] border-secondary and border-brand when selected. The no-bootstrap-border-with-tailwind-color lint rule reports the clash and autofixes it when the same string sets a base colour.

    The brand colour in SCSS

    Bootstrap compiles $primary (and $primary-N) from a static default green (primary in colors.json, css: false). The tenant's brand is the runtime --brand-* ramp, which Sass never sees. Anything that paints $primary therefore shows the default green, whatever the tenant configured. So:

    • In custom SCSS, paint brand with the semantic brand tokens — var(--bg-brand-solid), var(--border-brand-solid), var(--fg-brand-primary), var(--text-brand-secondary) — or a runtime step, var(--brand-600). For a tint that inverts like $primary-50 did, write var(--brand-50) with a dark-theme override to var(--brand-900). For a focus glow, use color-mix(in srgb, var(--focus-ring-color) 25%, transparent).
    • Never pass a CSS variable into a Sass colour function (tint-color, shade-color, mix, rgba($x, …)): they need a compile-time colour. That is why the static $component-active-bg (the default green, which Bootstrap tints) stays a literal.
    • src/styles/bootstrap/_variables.scss already points the Bootstrap outputs that would otherwise paint the static green at the runtime brand: the active list-group row and the range thumb.

    Font size

    One scale, pinned in physical pixels in primitives/typography.css (@theme static) to prevent distortion under Waldur's forced 13px root font size (html, body { font-size: 13px !important; }):

    Token Size Line Height Tailwind Class Former Bootstrap Utility
    --text-xs 12px 18px text-xs fs-7, fs-8
    --text-sm 14px 20px text-sm fs-6
    --text-base 16px 24px text-base fs-4, fs-5
    --text-lg 18px 28px text-lg fs-3
    --text-xl 20px 28px text-xl fs-2
    --text-2xl 24px 32px text-2xl fs-1, fs-1x
    --text-3xl 30px 36px text-3xl —
    --text-4xl 36px 44px text-4xl —
    • No Bootstrap fs-*. Bootstrap's fs-1 through fs-8 classes are retired and replaced by standard Tailwind text-* classes via the waldur-custom/require-font-size-scale ESLint rule.
    • Why pinned in pixels? Default Tailwind uses relative rem units (e.g. text-lg is 1.125rem). With an unpinned root, 1.125rem at 13px resolves to 14.625px instead of the intended 18px. Pinned declarations ensure consistent typography across both desktop (13px root) and mobile (12px root).
    • No arbitrary text-[14px]. Named scale tokens (text-sm) must be used instead.
    • No inline fontSize on JSX elements: static font sizes must use standard utility classes. Dynamic scaling (such as proportional avatar placeholder text or country flag emojis) requires an explicit eslint-disable with rationale.

    Font weight

    One scale, the five weights fonts.css loads (Inter 300–700), declared in primitives/typography.css:

    Weight Utility SCSS Use
    300 font-light var(--font-weight-light) Display text only
    400 font-normal var(--font-weight-normal) Body
    500 font-medium var(--font-weight-medium) Labels, emphasis
    600 font-semibold var(--font-weight-semibold) Headings, titles
    700 font-bold var(--font-weight-bold) Strong headings, figures
    • No Bootstrap fw-*. Bootstrap no longer emits them. Its names meant other weights than Tailwind's: Metronic's fw-bold was 500, fw-bolder 600, fw-boldest 700, while Tailwind's font-bold is 700. The same word painted two weights, and the fw-* classes were !important. fw-semibold and fw-medium never existed at all (they painted nothing).
    • No other steps. The theme clears Tailwind's thin, extralight, extrabold and black, so those classes compile to nothing, and an arbitrary font-[600] is reported: Inter is not loaded at other weights, and the browser would only fall back to the nearest loaded one.
    • No inline fontWeight on a JSX element: it outranks every stylesheet. Chart and PDF options (ECharts fontWeight) are not styles and keep their own.
    • SCSS reads var(--font-weight-*): stylelint rejects a number or keyword in component SCSS, and src/tailwindBootstrapColors.test.ts checks the compiled Metronic CSS (which stylelint skips). Metronic's $font-weight-* variables point at the tokens, keeping its names: its $font-weight-bold is var(--font-weight-medium) (500), $font-weight-bolder semibold, $font-weight-boldest bold.
    • A utility does not outrank an unlayered stylesheet (a component's .scss imported from TSX), where fw-*'s !important used to. Where such a rule sets the weight of the same element, drop the weight from the rule, or, if the rule is right for everything else it matches, use the important modifier on that element (font-normal!) with a comment.

    Corner radius

    All corner radius steps are pinned to physical pixels in primitives/radius.css (@theme static) to prevent fractional rem compression under Waldur's forced 13px root font size (html, body { font-size: 13px !important; }):

    Token Size Tailwind Class Former Class / SCSS Variable Use
    --radius-none 0px rounded-none rounded-0 Square corners, flush card attachments
    --radius-xs 2px rounded-xs — Subtle inner corners, tiny tags
    --radius-sm 4px rounded-sm $border-radius-xs (4px) Compact inputs, checkboxes, small indicators
    --radius-md 6px rounded-md $border-radius-sm (6px) Standard buttons, form controls, dropdown items
    --radius-lg 8px rounded-lg $border-radius / -lg (8px) Cards, panels, dialog headers, table containers
    --radius-xl 12px rounded-xl $border-radius-xl (12px) Prominent cards, thread bubbles, chat panels
    --radius-2xl 16px rounded-2xl $border-radius-2xl (16px) Large feature cards, hero containers
    --radius-modal 20px rounded-modal — Sidebar mode-switcher card
    --radius-full 9999px rounded-full rounded-pill, rounded-circle Avatars, pills, circular badges, status dots
    • No Bootstrap rounded-0, rounded-pill, rounded-circle. Bootstrap radius utilities are retired and replaced by Tailwind rounded-none and rounded-full via waldur-custom/enforce-border-radius-tokens.
    • Why pinned in pixels? Default Tailwind radii use relative rem units (e.g. rounded-sm is 0.25rem, rounded-xl is 0.75rem). Under Waldur's forced 13px root font size, unpinned rem tokens shrink unintentionally (rounded-sm becomes 3.25px, rounded-xl becomes 9.75px). Pinning the scale preserves crisp, consistent corner geometry.
    • SCSS variables (src/styles/bootstrap/_variables.scss) mirror the design tokens: $border-radius-xs is 4px (--radius-sm), $border-radius-sm is 6px (--radius-md), $border-radius and $border-radius-lg are 8px (--radius-lg), $border-radius-xl is 12px (--radius-xl), and $border-radius-2xl is 16px (--radius-2xl).
    • No inline borderRadius in JSX elements. Use standard utility classes (rounded-sm, rounded-md, rounded-lg, etc.).

    Duplicate roles. Two semantic tokens with the same value in both themes are one role with two names until shown otherwise. The audit fails on any such group not listed in DUPLICATE_BASELINE, and on a listed group that is no longer a duplicate (prune it). Either merge the tokens, or add the group with the reason the roles must stay separate — today: a surface and a hairline that share gray-100, a surface and a drawn line at gray-200, the brand border/icon/focus ring, and the strong divider and --text-quinary.

    Dark pairs. A ramp step, white/black, a hex or a raw var(--color-*-N) / var(--brand-N) is the same colour in both themes. require-dark-pair reports one that has no dark: utility for the same property, under the same other variants, in its class list (the className, the cn() call or the class-map entry it belongs to). Prefer the semantic utility the message names (bg-primary, bg-brand-subtle, text-brand, text-danger, …); keep a physical step only with its dark mirror (ring-brand-50 dark:ring-brand-900). A solid fill (bg-* at 400 or stronger) and white or black text on one read the same in both themes and pass. Tests are exempt: they assert class names, nothing renders.

    Seeing the tokens

    Storybook, group Foundations, stories in packages/design-tokens/src/*.stories.tsx:

    • Colors — the primitive ramps, one page per family in the same swatch style (step, resolved hex, variable name on hover): Neutral (gray, gray-dark and a side-by-side comparison), Status (success, warning, error, info), Accent (the decorative hues) and Brand (the runtime --brand-* ramp). Driven by tokens/colors.json.
    • Semantic Colors — Text, Backgrounds, Borders, Brand and the Status matrix: every role with its Tailwind utility, its light and dark source values, the value the page resolves now, and (for text, brand and status) its live WCAG contrast.
    • Typography — the type scale and the pinned --text-* tokens; Elevation — every shadow; Layout — spacing, radius, breakpoints and the z-index layers; Component Tokens — one page per components/*.css file.

    Everything but the ramp swatches and the type specimens is read from the token stylesheets themselves (stories/tokenSource.ts parses them through Vite's ?raw import), so a token added, renamed or re-pointed shows up with no story edit, and its comment becomes its description. tokenSource.test.ts checks that the parser keeps every declared token and that every component token file has a page.

    They live with the tokens they document, so a token change and its story change land in one package.

    What is not generated (yet)

    • The brand ramp — --brand-* is tenant-configurable and injected at runtime (initBrandTokens()).
    • The semantic layer — --border-*/--text-*/--btn-*/--status-* CSS files consumed directly across stylesheets and components (see Semantic roles), and the Tailwind bridge to them in tailwind/theme.css.
    • Non-colour scales — spacing, type, radii, shadows.

    Where a token file lives

    Tokens are hand-written CSS files. Dark mode lives in the semantic layer only: a semantic file holds both themes, a :root block and a :root[data-theme='dark'] block that redeclares only what differs, and reads ramp steps (var(--color-gray-100)) and the runtime brand variable, never raw hex (the modal backdrop is the one exception, as no ramp covers it). A component file has a single :root block whose colours read semantic roles, and switches theme through them.

    Tokens come in three tiers (a 3-layer architecture):

    1. Primitives (primitives/): Raw scales and foundational values: colour ramps, the brand fallback, typography, spacing, radius, breakpoints, z-index.
    2. Semantic roles (semantic/): Theme-aware roles, one file per concern: neutral surfaces, lines and text (background.css, borders.css, text.css), brand.css (every brand role and the focus ring), status.css, elevation.css.
    3. Component tokens (components/): Dedicated tokens scoped to specific waldur-ui component families.

    Components read semantic roles or component tokens, never a raw ramp step. Each layer reads only the layer below it, so a colour resolves in at most two hops: component → semantic → primitive.

    All tokens live in packages/design-tokens/src/css/ structured into three layer folders, each with an aggregate index.css. Two more locations hold what is not a token: fonts.css (@font-face rules) and tailwind/ (Tailwind wiring: the semantic utilities, custom variants, keyframes and motion utilities). Files in primitives/, semantic/ and components/ declare custom properties only.

    Layer Directory Files
    1. Primitives primitives/ colors.css, colorRamps.css, typography.css, spacing.css, radius.css, breakpoints.css, zIndex.css
    2. Semantic semantic/ background.css, borders.css, text.css, brand.css, status.css, elevation.css
    3. Components components/ button.css, card.css, check.css, dialog.css, menu.css, progress.css, sheet.css, sidebar.css, tab.css, table.css
    Not tokens root, tailwind/ fonts.css; tailwind/theme.css, tailwind/variants.css, tailwind/animations.css

    index.css aggregates everything: fonts.css, the three layers, then tailwind/theme.css, tailwind/variants.css and tailwind/animations.css. Every app imports it, so adding a token to its layer, or a utility to tailwind/, reaches all consumers. A component file is named after its waldur-ui family (button.css, not buttonColors.css): it may hold sizes and shadows as well as colours.

    App-only colours (read by one component in src/) don't need a token: write Tailwind utilities with the dark: variant at the call site, e.g. text-brand-600 dark:text-brand-300.

    Rules for a new token:

    1. Read by one call site in src/? Use Tailwind utilities with dark:, no token.
    2. Read by a waldur-ui component, or by several call sites? Add it to packages/design-tokens, in the file for its domain or component, prefixed by its owner (--card-*, --table-*).
    3. Import a new file from index.css, which stays a categorized list of imports.
    4. Keep the Metronic source note and the light and dark values in the same file.
    5. If it is a sidebar style token (--nav-*, --sidebar-bg) it must not be theme-scoped. Add new files to FILES in sidebarTheme.test.ts, which checks this.
    6. Custom properties (--*) must not be declared in stylesheets outside packages/design-tokens/ (enforced by Stylelint's property-disallowed-list).
    7. One hop per layer, never sideways: a semantic token binds to primitive ramps (--color-*), runtime scales (--brand-*) or raw CSS values, never to another semantic domain's token; a component token binds to a semantic token, never to another component's token (auditRedundantAliases, enforced by tokenAudit.test.ts).
    8. Component tokens don't handle dark mode: no [data-theme] selector in components/, and no colour from below the semantic layer (var(--color-*), var(--brand-*), hex, rgb(), color-mix()). If no semantic role has the light and dark pair a component needs, add the role to semantic/ first. Sidebar style blocks ([data-sidebar-style]) are exempt: they are fixed looks that must not follow the theme. Enforced by auditComponentLayer in tokenAudit.test.ts; files not yet converted are listed in COMPONENT_LAYER_RATCHET in scripts/audit-tokens.mjs, which only shrinks. When converting a file, map each token by its light and dark values, not by name.

    progress.css holds the --progress-* fills, track, label colours and heights; progressTokens.test.ts checks that every variant has a fill and label, that fills match Badge solid, and that labels stay readable.

    Retiring --bs-*

    Bootstrap's --bs-* custom properties are generated from the Metronic SCSS, so they sit outside the token architecture: the grays behind them are the same in both themes (dark-on-dark in dark mode), and some are never defined (--bs-tertiary-bg, --bs-secondary-bg, --bs-secondary-color, --bs-card-bg, --bs-heading-color), which makes a declaration that reads them silently resolve to nothing.

    Read the design tokens instead:

    --bs-* Token
    --bs-border-color --border-secondary
    --bs-body-bg --bg-primary
    --bs-body-color --text-primary
    --bs-primary, --bs-primary-N --brand-color, --brand-N
    --bs-gray-100 / -200 --bg-tertiary / --bg-quaternary
    --bs-gray-200 / -400 drawn as a line --border-divider / --border-divider-strong
    --bs-gray-50 --bg-secondary
    --bs-gray-400 / -500 / -600 / -700 --text-quinary / -quaternary / -tertiary / -secondary
    --bs-dark --text-primary
    --bs-success / -danger / -active-warning --status-success-fg / -danger-fg / -warning-fg
    --bs-primary-rgb --brand-color-rgb (follows the tenant brand)

    Never swap a --bs-gray-N for --color-gray-N: neither follows the theme. Pick the role token by what the colour paints, not by its gray step: a connector or handle that read --bs-gray-400 is --border-divider-strong, not the muted text role. A one-off with no role (a --bs-gray-300 guide line, --bs-dark as a border) gets the ramp step plus its gray-dark mirror at the call site.

    Two checks keep new reads out: the waldur-custom/no-bootstrap-css-vars ESLint rule (TS/TSX, including getCssVar('--bs-…')) and stylelint's declaration-property-value-disallowed-list and property-disallowed-list (CSS/SCSS). stylelint has no ignore list, so both apply to src/styles/bootstrap/** too: the few places that must set one of Bootstrap's own hooks (the .table custom properties) carry a stylelint-disable comment saying why. The ESLint rule has no exemption either and checks all TS/TSX.

    Outside that SCSS nothing reads them any more, so neither check has a per-file allow list.

    Adding or changing a value

    1. Edit tokens/colors.json.
    2. yarn tokens:generate.
    3. Commit the JSON and the generated file together.

    Changing a light value changes what the app renders in both Bootstrap and Tailwind components at once, which is the point. A new ramp or step appears in CSS as --color-<name>-<step> (and so as Tailwind utilities). Sass defines no colour ramp. Every Sass colour variable (tokens as var(--…), plus $white, $black and the static default green) lives in src/styles/bootstrap/_variables.scss, and Bootstrap's own defaults fill every other $gray-* / $primary name, none of which reaches a compiled rule.

    Verifying a refactor changes nothing

    When the generator, the data model or the Metronic SCSS changes and no pixel should move, snapshot the Metronic stylesheet before and compare after:

    1
2
    node scripts/color-diff.mjs save /tmp/before.json   # on the base commit
node scripts/color-diff.mjs compare /tmp/before.json

    It compiles src/styles/bootstrap/index.scss and records what every declaration resolves to in each theme, with the design tokens and the dark-theme / light-theme overrides applied, so a change that keeps the rendered colour (a token in place of an SCSS gray of the same value) reports nothing. For the CSS side, compile src/tailwind.css with @tailwindcss/node and diff the emitted --color-* declarations.

    Metronic stylesheets consume CSS custom properties directly (var(--text-primary), var(--bg-primary), var(--border-primary), etc.), ensuring identical token resolution across both Metronic and Tailwind components.
